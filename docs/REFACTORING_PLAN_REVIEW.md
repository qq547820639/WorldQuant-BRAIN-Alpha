## 五、潜在风险分析

### 5.1 方案执行风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| P1-3 修复范围过大，引入新循环依赖 | 中 | 高 | 将 P1-3 拆分为 2 个文件（精确匹配）和 3 个文件（相关模式），分步修复 |
| Phase 3 Mixin 合并导致 MRO 冲突 | 中 | 高 | 合并前用 `inspect.getmro()` 验证每个合并的 MRO；保留原始 mixin 文件为别名 |
| JobStore 迁移中数据丢失 | 低 | 严重 | 双写模式（同时写 JSON + SQLite），验证一致性后切换 |
| 前端代码被忽略导致整体质量不均衡 | 中 | 中 | Phase 4 追加前端审计任务 |
| 文档清理误删导致上下文丢失 | 中 | 低 | 使用 `docs/archive/` 目录归档而非直接删除 |

### 5.2 方案本身的结构性风险

1. **范围蔓延风险**：方案聚焦 Python 后端，但项目实际包含前端（React + 内联 JS）、Shell 脚本、MJS 浏览器测试等多语言代码。重构仅覆盖 Python 可能造成质量不均衡。
2. **双轨前端未处理**：维护两套前端（内联 HTML/JS + React）是最大的架构复杂度来源之一，方案完全未涉及。
3. **过度依赖现有门禁**：方案假设 `quality_gate.py` 和 `final_release_gate.py` 能捕获所有回归，但这些工具本身也有 719 + 600 行代码，可能存在盲区。

3. **修正数字声明**：
   - pipeline.py 导入数：56 → 54
   - 缺少 `__future__` 的文件：17 → 6
   - 低于 50 行的测试文件：15-20 → 28

### 6.2 补充分析（增强覆盖）

4. **追加前端代码诊断**（建议列为 Phase 5 或 Phase 4 追加任务）：
   - React/TS 代码：组件复杂度、状态管理、API 契约一致性
   - 内联 JS 代码：`app.js` 等文件的质量评估
   - 双前端同步机制：契约测试覆盖
5. **追加安全审计**：
   - 凭证管理路径审查
   - CSRF/CSP 配置审计
   - 日志脱敏覆盖率验证
6. **建立性能基线**：
   - 记录当前 `import brain_alpha_ops` 耗时
   - 记录 `build_prod.py` 构建耗时
   - 记录 `quality_gate.py --full` 运行耗时
   - 记录核心 API 端点响应时间

### 6.3 执行优化

7. **添加时间缓冲**：每阶段预留 20% 缓冲（Phase 1: 2.5周, Phase 2: 2.5周, Phase 3: 3周, Phase 4: 2.5周 → 总计 10.5 周）
